# ADR-047 — Tab-Bar Icons: `lucide-react-native` (Not `@tamagui/lucide-icons`), Two Real Build Incompatibilities Found and Fixed

**Date:** 2026-07-06
**Status:** Accepted — probed twice (dependency-resolution probe, then a real dev-server bundle-fetch probe); both rounds found real issues, both fixed
**Bolt:** 9 — Navigation, i18n & Design Retrofit (Layer 2 finding #1)

## Context

The user's Layer 2 (device) manual verification pass found the bottom tab bar rendering `@react-navigation/bottom-tabs`' own generic default icon (a downward-triangle placeholder) instead of a real icon per tab. Root cause, confirmed by reading `main-tab-navigator.tsx` directly: none of the three `Tab.Screen` entries set `tabBarIcon`, and no icon library existed anywhere in the project.

## Decision — icon library

`@tamagui/lucide-icons` was the natural first candidate (already-installed `tamagui`, themed components). **Probed before installing for real** (this project's standing discipline, ADR-045's own precedent): `@tamagui/lucide-icons` has **no `2.x` release line at all** — its latest version, `1.144.4`, depends on `@tamagui/core@1.144.4`/`@tamagui/web@1.144.4`, a completely different major line from this project's pinned `tamagui@2.4.2`. Installing it for real and inspecting the resulting `node_modules` tree confirmed a full nested duplicate `@tamagui/core@1.144.4`/`@tamagui/web@1.144.4` under `node_modules/@tamagui/lucide-icons/node_modules/@tamagui/` — a second, isolated Tamagui rendering engine with its own React Context, which would not correctly resolve theme tokens from this app's real `TamaguiProvider` (a different module instance entirely). This is the same risk class as the React-Query/`react-native-svg` MF-singleton incidents (ADR-034, Bolt 8), just surfacing via a nested `node_modules` duplicate instead of Module Federation.

**Decision: `lucide-react-native`** (the plain, non-Tamagui-wrapped Lucide icon set) instead. Confirmed via `npm view`: zero dependencies of its own, peer deps only on `react`/`react-native`/`react-native-svg` (`^12.0.0 || ... || ^15.0.0`, already installed and MF-shared since Bolt 8). Each icon is a stateless SVG render (confirmed by reading `lucide-react-native`'s own `Icon.js` — it renders `react-native-svg`'s `<Svg>`/`<Path>` directly, no Tamagui coupling at all), so it needs no Provider and carries none of the shared-singleton *correctness* risk `tamagui`/`i18next` do.

## Decision — MF shared-singleton placement

Host-only (`rspack.config.mjs`). Only the host's tab bar uses icons; this bolt's `pools`-remote design polish (Layer 2 finding #4) used existing Tamagui primitives, not icons, so `rspack.config.pools-remote.mjs` is unchanged. Unlike `tamagui`/`i18next`, this is a bundle-size nicety, not a bug-avoidance requirement, should a future bolt add icons to `pools` too (no shared React Context needed for a stateless SVG icon to render correctly).

## Probe #2 — real dev-server build, not just a static bundle (two further real incompatibilities found and fixed)

Per the standing lesson from this bolt's own earlier `react-dom` incident (a static `npx react-native bundle` build succeeded but the app crashed at real boot) — **the same class of gap recurred here**, twice:

1. **`ReanimatedPlugin` + `lucide-react-native` = Hermes-parser failure.** A real `yarn start` dev-server build (not a static bundle) failed: `SyntaxError: Can't create duplicate variable that shadows a global property: 'Infinity'` in `lucide-react-native/dist/esm/icons/infinity.mjs` (`const Infinity = createLucideIcon("Infinity", ...)` — ordinary, valid JS that Hermes' parser alone rejects). Root cause: `@callstack/repack-plugin-reanimated`'s `ReanimatedPlugin` (added post-Implement per ADR-045's own follow-up) injects a module rule matching **every** non-`react`/`react-native` JS/MJS file in the entire dependency graph (confirmed by reading `@callstack/repack-plugin-reanimated/dist/rules.js` directly), parsing each one via `hermes-parser` — not scoped to reanimated-related files at all. **Fix attempted first: `new ReanimatedPlugin({ unstable_disableTransform: true })`** (exactly what the plugin's own emitted warning recommends when paired with `babel-swc-loader`, which this project already uses). This did **not** fix the error — it only changed which loader reported it.
2. **The project's own primary loader has the identical problem, independent of `ReanimatedPlugin`.** After disabling `ReanimatedPlugin`'s rule, the *exact same* Hermes-parser error still occurred, now reported from `@callstack/repack/babel-swc-loader` itself — this project's own main `module.rules` entry, applied (with no exclusions at all, before this fix) to literally every `.js`/`.jsx`/`.ts`/`.tsx` file in the project, including all of `node_modules`. This loader's underlying parser is also Hermes-based. **Fix: excluded `lucide-react-native` from this rule** (`exclude: /node_modules[\\/]lucide-react-native/`) — safe because the package ships plain, already-valid modern JS/ESM with no JSX/TS/Flow syntax to strip, so it needs none of this loader's transform pipeline; Rspack's own native module handling parses it directly.

Both fixes were verified against a **real, running dev server** (`yarn start`), not a static build: the dev server compiled both `ios`/`android` with zero errors (only the same pre-existing-class advisory warnings), and the actual served bundle was fetched (`curl http://localhost:8081/index.bundle?platform=ios&dev=true`, ~17MB) and inspected directly — confirmed 3496 `createLucideIcon` occurrences (every icon definition bundled successfully), the existing `react-dom` shim's `flushSync` still present (21 occurrences, unaffected by this change), and the only `"Cannot find module"` string in the entire bundle is the pre-existing, already-guarded `@react-native-masked-view` `IgnorePlugin` stub (safe, unchanged from before this bolt — confirmed guarded by a `try/catch` in `@react-navigation/elements`, per `rspack.config.mjs`'s own long-standing comment).

## Consequences

- `package.json` gains `lucide-react-native` as a direct dependency (and briefly gained, then removed, `@tamagui/lucide-icons` — `yarn.lock` reflects only the final state).
- `rspack.config.mjs` gains: the `lucide-react-native` shared-singleton entry (host-only), `ReanimatedPlugin({ unstable_disableTransform: true })` (was previously constructed with no options — this is a required correctness fix now, not a nicety, though it alone did not resolve the Hermes-parser issue), and an `exclude` on the primary loader rule scoped narrowly to `lucide-react-native`.
- **Lesson, reinforcing ADR-045's own**: a successful static `npx react-native bundle` run is not sufficient evidence a change is safe on this stack — only a real dev-server build (or better, a real device/simulator run) exercises every actual loader/plugin combination. This is the second time in this same bolt a static-build-only probe would have missed a real, boot-blocking issue.
- If a future bolt needs icons inside the `pools` remote, re-run this same two-round probe (dependency-resolution AND real dev-server build) against `rspack.config.pools-remote.mjs` — do not assume the host's fix automatically covers a second bundle.
