# ADR-003 — Sign-in/sign-up/resend classification logic lives in `domain/`, not `platform/`

## Context

AUTH-1 requires that sign-in/sign-up outcomes be classified into specific domain states (`unconfirmed-email` distinct from generic `invalid-credentials`; `pending-confirmation` distinct from a generic error) rather than passed through as raw Supabase SDK responses/errors. `model.md §2` already defines `SignInResult`/`SignUpResult`/`ResendAttemptResult` as plain discriminated unions. The question this ADR resolves: does the *logic that produces* these values (reading a raw Supabase error/response and deciding which union member it maps to) live in `src/domain/auth/` or in `src/platform/supabase/supabase-adapter.ts`?

## Decision

The classification functions (`classifySignInError`, `classifySignUpError`, `evaluateResendAttempt`) live in `src/domain/auth/sign-in.ts` / `sign-up.ts` / `resend-cooldown.ts` — pure functions, framework-free, with no Supabase SDK import. `src/platform/supabase/supabase-adapter.ts` (which **does** import the Supabase SDK) imports these domain functions and calls them internally, so the adapter's public auth methods return the already-classified `SignInResult`/`SignUpResult` directly — no feature module or screen ever sees a raw Supabase error object.

Dependency direction: `platform/supabase/supabase-adapter.ts` → imports → `domain/auth/sign-in.ts`. Never the reverse. This is the same inward-pointing rule ADR-001 (Bolt 0) already establishes for the whole repo, applied here to a logic boundary that could plausibly have gone either way.

## Consequences

- The classification logic is unit-testable as plain TypeScript (`__tests__/sign-in.test.ts`, etc.) with hand-constructed fake SDK error shapes as input — no Supabase client, no React Native runtime, no mocking of `@supabase/supabase-js` required to verify "this specific error message/code maps to `unconfirmed-email`, not `invalid-credentials`." This is the same testability rationale `model.md`/Bolt 0's `auth-claims.ts` already established for the tri-state claim helpers.
- The adapter (`platform/`) stays a thin translation layer: call the SDK, hand the raw result to the domain classifier, return what comes back. If Supabase's SDK ever changes its error shape (a documented adapter-boundary concern per `system-context.md §2`), only the *call site* inside the adapter needs to change — the classification rules themselves (what counts as "unconfirmed," what stays generic for anti-enumeration) do not move.
- **Resend-cooldown enforcement specifically routes through `BackendApiClient`, not the Supabase adapter** (resolved at the Design checkpoint, see `design.md §2`/open question 3): cooldown is explicitly *not* a Supabase Auth built-in (`system-context.md §3`'s capability table lists it under "Auth flows requiring server logic beyond Supabase Auth itself"), so `src/platform/backend-api/backend-api-client.ts` gains a call like `backendApiClient.request<ResendAttemptResult>({ capability: 'auth.resendConfirmation', body: { email } })`, consistent with Bolt 0's capability-naming convention (`model.md`'s `BackendApiClient` contract — stable capability names, not URLs). `evaluateResendAttempt` (domain) is still the function that interprets the response shape into `ResendAttemptResult`; only the transport changed from "Supabase adapter" to "Backend-API client," the domain/platform split itself is unchanged. The Supabase adapter stays strictly Supabase-only per `system-context.md §2` — it does not grow a cooldown-shaped method.
- A reviewer's question for any PR touching sign-in/sign-up/resend stays simple and consistent with Bolt 0's existing precedent: "is the classification logic free of SDK/network imports, and does only the adapter/client call into it (never the reverse)?"
